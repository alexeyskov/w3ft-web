# Интерфейс Warcraft runtime

В проекте есть настоящий WASM-модуль и браузерный host. При запуске с сайта работают оригинальные ролики, меню и первая глава Frozen Throne «Наги»: вступительная сцена, выбор героя, движение и сохранение/восстановление после перезапуска Chromium. Проверен также LAN-матч двух Chromium на Echo Isles с добычей ресурсов, боем и победой после отключения соперника. Полная совместимость режимов ещё не подтверждена: `createGame()` отклоняет запуск, а `/api/status.runtime.playableVerified` остаётся `false`.

## Пакет и профиль бинарников

`tools/package_runtime.py` размещает в `var/runtime/` ES-модули из `web/runtime/` и следующий manifest рядом с собранными `wc3.wasm` и `build.json`:

```json
{
  "abi": "wc3-browser-v1",
  "module": "client.mjs",
  "wasm": "wc3.wasm",
  "wasmCompat": "wc3-compat.wasm",
  "diagnostics": true,
  "graphics": "webgl2",
  "capabilities": { "campaign": false, "skirmish": false, "multiplayer": false }
}
```

Сервер разрешает локальные basename, проверяет ABI и WASM magic/version. `installed=true` подтверждает наличие допустимого пакета, а не работоспособность игры.

**Сборка для браузеров без хвостовых вызовов.** `wasmCompat` необязателен. Это тот же код, собранный `tools/build_runtime.py --variant compat` (`make runtime` собирает обе) для движков без хвостовых вызовов WebAssembly: Safari до 18.2, Chrome до 112, Firefox до 121. Лифтер записывает переход по адресу из регистра или памяти (x86 `jmp eax`, в том числе по таблице `switch`) как `DISPATCH_TAIL`. В обычной сборке это `return_call`. В совместимой (`-mno-tail-call -DWC3_TAIL_TRAMPOLINE=1`, `runtime/cpu.h`) переход только запоминает цель в `_Thread_local wc3_tail_pending` и возвращается, а цель вызывает вызывающая функция. Для этого сборщик компилирует копию каждого шарда, где после каждого прямого вызова `sub_XXXXXXXX(c);` стоит `TAIL_RESUME(c);`. Другие формы вызова функции игры он отвергает. `dispatch_indirect` проверяет то же сам. Стек не растёт: цикл по `switch` в обычной сборке занимает один кадр. Без трамплина он рос бы на кадр с каждым проходом. Переходы в гостевом коде, `record_dispatch` и бюджет вызовов те же, что в обычной сборке. `build-compat.json` описывает сборку так же, как `build.json`; в нём нет `+tail-call` в `features`. `package_runtime.py` вносит `wasmCompat` в manifest, только если обе сборки сделаны из одних исходников, заголовков, модулей и тем же компилятором, а SHA-256 файла совпадает; иначе упаковка останавливается. `GET /api/status` добавляет к `runtime` поля `compatWasmUrl` и `compatWasmSize`. Отсутствующий или повреждённый файл не мешает обычной сборке, тогда этих полей нет. Страница проверяет поддержку `WebAssembly.validate` маленького модуля с `return_call`. Без неё она передаёт `compatWasmUrl` в `prepareGame` и `runDiagnostics` и показывает предупреждение о режиме совместимости. Если совместимой сборки нет, кнопка «Играть» неактивна, а игрок видит просьбу обновить браузер. Worker пишет в журнал имя модуля: `WASM wc3-compat.wasm compiled in … s`. Manifest не загружается посетителями; включать capability до проверки соответствующего режима нельзя.

`build.json` содержит SHA-256 WASM, параметры сборки/памяти и `modules[]` с именем, image base, SHA-256 и каталогом перевода каждого PE. Перед загрузкой `engine.mjs` самостоятельно вычисляет SHA-256 всех исходных PE и проверяет полноту/совпадение профиля. Это защищает от исполнения переведённого кода с другой установкой. SHA-256 самого WASM записывается builder, но при каждом браузерном запуске автоматически не сверяется.

Текущий пакет включает четыре исходных образа: `war3.exe`, `game.dll`, `Storm.dll`, `ijl15.dll`. Их гостевые адреса сохраняются; PE loader копирует секции, обрабатывает relocations, exports и IAT по именам/ordinal. Для внешних библиотек host выдаёт thunks. Отсутствующий обработчик вызывает fault при обращении. Miles подключён частичным HLE-адаптером, оригинальный `Mss32.dll` в текущий WASM не входит.

## Диагностический запуск

`client.mjs` экспортирует `async runDiagnostics(options)`, возвращающий `{ async stop(), finish(), key(type, {keyCode, text, extended}) }`. `key` передаёт игре нажатие (`keydown`/`keyup`, код виртуальной клавиши 0–255, на `keydown` текст до 8 символов) так же, как клавиатура над canvas; через него работают экранные кнопки и клавиатура устройства на сенсорных экранах. Параметры:

| Поле | Назначение |
| --- | --- |
| `canvas` | HTMLCanvasElement; передаётся в Worker как OffscreenCanvas. Пока canvas внутри полноэкранного элемента, runtime захватывает указатель (Pointer Lock) и передаёт относительное движение, ограниченное краями canvas; без захвата события родителя canvas (чёрные поля) прижимаются к краям. В окне ввод принимает только сам canvas |
| `wasmUrl` | По умолчанию `/runtime/wc3.wasm` |
| `saves` | SaveStore: `list()` возвращает файлы; `applyChanges({files,deleted})` атомарно записывает изменения, либо используются `write`/`remove` |
| `map` | Необязательная карта каталога с `path`, `size`, `downloadUrl` |
| `transport` | Необязательный FrameTransport; без него используется приватный loopback |
| `audioEnabled` | По умолчанию `true`; `false` отключает финальный микс и звук видео, сохраняя Miles и его таймеры |
| `audioContext` | Необязательный AudioContext, созданный во время щелчка «Играть»: звук может стартовать после долгих загрузок, когда щелчок уже не считается активацией. Его закрывает тот, кто создал |
| `media` | Необязательный `Map` пути ассета (`/api/assets/{id}`) в URL его копии на устройстве (`prepareGame`); ролик играет из копии, иначе с сервера |
| `language` | Необязательный язык игры (`ru`, `en`): Worker запрашивает `GET /api/assets?language=…`, и сервер подставляет архивы и ролики этой локализации вместо базовых. Без него — базовая установка |
| `resolution` | `{width,height}`, одно из `GAME_RESOLUTIONS` (`launch-settings.mjs`): 800×600, 1024×768 (по умолчанию API), 1152×864, 1280×960 (по умолчанию на сайте), 1400×1050, 1600×1200, 1920×1440, 2048×1536; начальный видеорежим и реестр Warcraft. `EnumDisplaySettings` перечисляет все эти режимы |
| `batchGraphics` | По умолчанию `true`; асинхронный поток команд OpenGL в общей памяти, `false` — каждый GL-вызов синхронно в broker (для сравнения) |
| `vsync` | По умолчанию `true`: broker исполняет SwapBuffers по `requestAnimationFrame` своего Worker, то есть выводит не больше одного кадра за обновление экрана; скрытая страница без rAF выводит кадр через 40 мс. `false` выводит кадры сразу (замер пропускной способности) |
| `graphicsSettings` | Необязательный объект видеонастроек Warcraft в кодировке её реестра (`HKCU\Software\Blizzard Entertainment\Warcraft III\Video`): `modeldetail`, `animquality`, `texquality`, `particles`, `lights`, `spellfilter` — 0–2 (низко/средне/высоко), `unitshadows`, `occlusion` — 0/1, `gamma` — 0–100. Неуказанные значения не записываются, действуют умолчания `game.dll` |
| `onGraphicsSetting(name, value)` | Вызывается, когда игра записывает одно из этих значений (кнопка «ОК» в её «Настройки → Изображение»); сайт сохраняет его для следующего запуска |
| `maxFps` | `0` (по умолчанию) — кадр на каждое обновление экрана; `1–1000` — ограничение частоты: swap выводится не раньше `1000/maxFps` мс после предыдущего, на ближайшем обновлении экрана (или по таймеру, если `requestAnimationFrame` нет). Игра, опережающая вывод не более чем на кадр, идёт с этой частотой |
| `strictFinish` | По умолчанию `false`: `glFinish` исполняется как `gl.flush()`; `true` возвращает блокирующий `gl.finish()` с проверкой backend |
| `profileRpc` | По умолчанию `false`; `true` добавляет в `frame.execution.rpcByName` число и суммарную длительность синхронных broker-вызовов по именам импортов |
| `nativeTextureShader` | По умолчанию `true`; отдельная короткая программа для штатной фильтрации WebGL, полная программа остаётся для border sampling |
| `legacyClampToEdge` | По умолчанию `true` в Warcraft: профиль старого драйвера для `GL_CLAMP`; `false` возвращает нормативную выборку границы для диагностики |
| `graphicsDebugChecks` | По умолчанию `false`; `true` включает синхронную проверку backend WebGL после каждой операции |
| `timeout` | По умолчанию 30 000 мс; ограничение жизни диагностического Worker; `0` отключает лимит |
| `dispatchBudget` | По умолчанию 10 млн; лимит гостевых dispatch на поток, uint32; `0` отключает лимит |
| `onFrame(frame)` | Счётчики кадров/draw calls и размер после настоящего SwapBuffers |
| `captureGraphics` | Диагностический захват одного кадра и профилирование host-вызовов |
| `onStatus(text)` | Сообщения загрузки и ошибки |
| `onReport(report)` | Итоговая диагностика; `gameplayVerified` всегда `false` |
| `onScreenshot({name, blob, width, height})` | Снимок экрана Warcraft (Print Screen): игра пишет `Screenshots/WC3ScrnShot_<дата>_<время>_<n>.tga`, runtime передаёт его как PNG (`screenshot.mjs`). Сайт отдаёт файл в загрузки браузера |

Кнопка «Играть» передаёт canvas, сохранения, параметры и выбранное LAN-лобби, отключая диагностические лимиты (`timeout:0`, `dispatchBudget:0`). Один контроллер предотвращает параллельный запуск двух сессий. Кампания, сражение и карты выбираются в оригинальном интерфейсе Warcraft. Worker монтирует каталог карт сервера как папку `Maps/` игры (кампании `.w3n` — как `Campaigns/`), так же, как в установленной копии: список карт сразу открывается на папках каталога. Прежние пути `Maps/Web/…` и `Campaigns/Web/…` записаны в сохранениях, сделанных до 6 ноября 2026. Они остаются скрытыми псевдонимами: файл открывается по такому пути, но папка `Web` в списке не показывается. Дополнительный программный `map` также поддерживается для диагностики. После записи сохранений страница получает событие `warcraft-report` с отчётом в `detail`. Полноэкранным элементом служит обёртка игры, содержащая canvas, видео и панель управления. Размер canvas рассчитывается по его игровым пропорциям; поля находятся за его пределами.

Worker компилирует WASM прямо во время скачивания (`WebAssembly.compileStreaming`, нужен `Content-Type: application/wasm`; без него компилирует из байтов) и скачивает профиль и manifest ресурсов. Модуль не держится в памяти отдельным буфером на 180 МБ, как раньше всю игру. В JavaScriptCore (Safari, браузеры iOS) этот Worker раз в 0,5 с, а игровые потоки раз в 65 536 вызовов создают большой ArrayBuffer без записи (`webkit-gc.mjs`): иначе общая память WebAssembly, которую JavaScriptCore считает частью кучи, откладывает сборку мусора на гигабайты. Worker полностью загружает четыре PE, создаёт shared memory, проверяет SHA-профиль, связывает импорты, исполняет DLL entry points с `DLL_PROCESS_ATTACH`, затем entry point `war3.exe`. Текущая командная строка — `war3.exe -opengl -window`. `createRuntime()` и `tools/run_runtime.mjs` позволяют отдельно исследовать этот путь в Node.

**Касания** (`touch-input.mjs`). События с `pointerType === 'touch'` не идут по пути мыши. Касание — левый щелчок, долгое касание (500 мс) или касание двумя пальцами — правый, движение одним пальцем — перетаскивание левой кнопкой, движение двумя пальцами — удерживаемые стрелки (смещение больше 28 px, карта следует за пальцами), щипок — колесо мыши (шаг на 15% расстояния между пальцами). Перед каждым нажатием курсор ставится в точку касания, нажатие приходит через 70 мс, отпускание — ещё через 70 мс: Warcraft нажимает кнопку, только если WM_MOUSEMOVE уже поставил её под курсор. `pointercancel` и конец сессии отпускают удерживаемое. Pointer Lock запрашивается только при точном указателе (`any-pointer: fine`). Подробности и проверки — в [port-status.md](port-status.md#mobile-browsers).

Стартовая shared memory — 64 MiB, максимум — 4 GiB, гостевая область — `0x78000000` байт. Она начинается с адреса `0x04000000` (`wc3_memory_base()`) внутри окна 2 GiB, которое принадлежит только гостю: `wc3_init` растит память до 2112 МБ (`runtime/cpu.h`, `WC3_GUEST_BASE`/`WC3_GUEST_WINDOW`). Выделения runtime после этого (native-стеки потоков по 16 МБ, TLS) идут за окном. Гостевой код обращается к памяти по адресу с маской окна, без проверки границ. Требуются SharedArrayBuffer, WebAssembly atomics/tail calls и изоляция origin. `finish()` и `stop()` останавливают гостевые потоки, закрывают виртуальные сокеты с FIN, записывают файловый overlay в `saves` и освобождают Worker, аудио и обработчики транспорта. Если Worker не отвечает пять секунд, используется принудительное завершение. Участие в лобби сайта сохраняется до явного выхода из него. После передачи canvas в OffscreenCanvas для нового запуска нужен новый HTMLCanvasElement.

Отчёт содержит этап (`linked`, `dll-initialization`, `dlls-initialized`, `guest-entrypoint`, `guest-returned`, `guest-exited`), модули, регистры, хвост guest trace, счётчики host-вызовов и ошибку. `wasmExecuted` и `profileVerified` подтверждают работу загруженного reactor и проверку PE; они не являются признаком игрового меню. Штатный `ExitProcess(0)` возвращает `stage:"guest-exited"`, `exitCode:0`, `error:null`; ненулевой код сохраняется как ошибка. Список `unsupportedImports` отражает отсутствующие обработчики. Зарегистрированный API также может явно отклонять неподдерживаемый вариант вызова, поэтому этот список не исчерпывает ограничения.

## Графика, звук и Win32

`FixedFunctionGL` реализует часть OpenGL 1.x: матрицы/стеки, текстуры и mipmaps, две текстурные стадии ARB_multitexture, CLAMP с цветом границы, vertex/color/texture arrays, indexed draws, depth/blend/alpha, освещение и туман. Освещение по вершинам (до 8 источников, материалы обеих сторон, color material, прожекторы, затухание, local viewer, NORMALIZE/RESCALE_NORMAL) вычисляет вершинный шейдер; `_litColors` остаётся эталонной реализацией для пиксельных тестов. Клиентские массивы передаются рендереру в исходной раскладке гостя (`{raw:{position:{bytes,offset,type,size,stride},…}}`) и загружаются одним `bufferData` на draw; перекрывающиеся interleaved-массивы занимают одну область, тип UNSIGNED_BYTE нормализует WebGL. Прежний формат с `Float32Array` поддерживается, `floatAttributes()` преобразует новый формат для диагностики. Повторные изменения состояния WebGL, привязок текстур, указателей атрибутов и uniform-ов отфильтрованы. Отдельный framebuffer сохраняет back buffer между Worker RPC и выводит завершённый кадр при SwapBuffers. Оригинальные сцены меню уже рисуются; неподдерживаемые состояния по-прежнему вызывают явную ошибку. D3D8 backend отсутствует.

В Warcraft включён отдельный профиль `legacyClampToEdge`: `GL_CLAMP` использует поведение CLAMP_TO_EDGE старых Windows-драйверов. Захват с Echo Isles выявил текстуру тумана 16×16 с alpha230 и край UV0,9765625: нормативный CLAMP подмешивает прозрачную границу за последним центром texel0,96875, создавая светлую сетку. Профиль сохраняет текстуру и её гостевое состояние, убирая подмешивание границы; явный CLAMP_TO_BORDER остаётся полноценным. В самостоятельном FixedFunctionGL профиль выключен по умолчанию, строгие пиксельные тесты сохранены. При таком wrapping используется штатная фильтрация WebGL. Короткий shader исключает ветви программной выборки границы; любой активный stage с настоящим CLAMP/BORDER переключает draw на полную программу. Обе программы используют одинаковые attribute locations и собственные uniform locations. Тест сравнивает все пиксели десяти сцен, включая переключение программ и две текстурные стадии.

Все void-вызовы OpenGL гостевого потока (состояние, immediate mode, `glDrawElements`/`glDrawArrays`, `glTexImage2D`/`glTexSubImage2D`, `glDeleteTextures`, `glFlush`/`glFinish`, `wglSwapLayerBuffers`/`SwapBuffers`) записываются в поток команд Worker: 6 блоков по 4 MiB в SharedArrayBuffer (`graphics-batch.mjs`). Скалярные аргументы, матрицы и векторы фиксируются в момент вызова; draw захватывает индексы и используемый диапазон вершин всех включённых массивов (индексы сдвигаются к нему), загрузка текстуры — пиксели по зеркальному состоянию `glPixelStorei`. Поэтому исполнение записи позже не читает гостевую память. Запись, которую нельзя отложить (больше блока, неизвестное состояние, ошибка аргументов), уходит обычным синхронным вызовом, и ошибку сообщает broker. Запросы (`glGet*`, `glGetError`, `glIsEnabled`, `glGetString`, `glReadPixels`), `glGenTextures` и `wgl*` остаются синхронными.

Каждый синхронный импорт Worker несёт накопленный сегмент записей; broker ставит его в очередь до обслуживания импорта. Перед любым графическим обработчиком (opengl32, gdi32, `FillRect`, `ChangeDisplaySettings*`) хост исполняет всю очередь, в том числе когда GL вызывает гостевой код, исполняемый самим broker (оконные процедуры при `DestroyWindow`/`DispatchMessage`). Остальные импорты не ждут и не переупорядочивают GL-работу. В прочее время broker исполняет очередь порциями до 4 мс между задачами; общий счётчик ожидающих RPC прерывает порцию, как только Worker ждёт ответа. Swap отпускает гостя, когда broker выполнил предыдущий кадр (один кадр в полёте). С `vsync` broker начинает исполнять запись swap только после очередного `requestAnimationFrame`: каждый кадр держится на экране ровно одно обновление дисплея, а игра, ожидая подтверждения предыдущего кадра, не рисует лишних. Во время ожидания broker не планирует пустых задач (следующую порцию запускает сам rAF), иначе непрерывные MessageChannel-задачи вызывают паузы сборщика мусора Blink. Ошибка исполнения отложенной записи завершает процесс с именем импорта и адресом возврата исходного вызова. Отчёт `execution` содержит RPC-вызовы, число записей и сегментов; те же счётчики доступны в кадрах.

Miles-адаптер поддерживает PCM/sample API, WAV и MP3 streams через гостевые file callbacks. Потоки `Sound\Music\…` и `Sound\Ambient\…` читает служебный гостевой поток `wc3host.dll!MilesStreamThread`, по одному: `AIL_open_stream` возвращает их сразу, и они играют после декодирования (`WorkerAudio.createEncodedBufferAsync`, `Atomics.waitAsync`). Остальные потоки читаются и декодируются в вызове. `PCMPlayer` использует AudioContext: mono/stereo u8, s16le, f32le, volume/pan/rate, loop, play/pause/resume/stop и позицию в секундах. Пространственный ABI преобразует координаты и расстояния в WebAudio, реализует конус, затухание, Доплер, obstruction/occlusion и программную реверберацию. Не заявляется аппаратная EAX-совместимость. Окончание samples и streams (EOS) определяется по таймеру воспроизведения, а зарегистрированные callbacks гостя вызываются из отдельного служебного гостевого потока — как из timer thread настоящего Miles. Warcraft не опрашивает статус голосов: по EOS он освобождает sample в своём пуле и заканчивает анимацию говорящего портрета. Без этого реплики теряли связь с анимацией портрета, а пул samples исчерпывался и новые звуки не запускались. ASI/ADPCM для сжатых samples и XMIDI/DLS ещё не завершены.

`WorkerAudio` выполняет синхронный RPC через отдельный SharedArrayBuffer. Main thread исполняет операцию настоящего PCMPlayer и возвращает результат или ошибку с контекстом гостевого вызова; `Atomics.wait` используется только в Worker. Состояние и позиция берутся из WebAudio. Истечение timeout отменяет запрос и делает этот audio bridge недоступным.

Win32/CRT реализованы частично: память/heap с объединением свободных блоков, файловые операции, registry, handles, TLS, оконные сообщения, очередь клавиш, локаль en-US и строковые/математические функции. WM_ACTIVATEAPP посылается только при смене активного приложения; переход активности между окнами самой игры его не порождает. Иначе Warcraft считает себя свёрнутым и ограничивает главное меню 16–18 кадрами в секунду. Гамма — состояние дисплея: `GetDeviceGammaRamp`/`SetDeviceGammaRamp` хранят таблицу 3×256 вне GL-контекстов (Warcraft восстанавливает исходную таблицу при уничтожении окна, уже после `wglDeleteContext`), а renderer применяет её к выводимому кадру отдельным проходом; задний буфер и `glReadPixels` не меняются. Warcraft с `-window` не применяет свою настройку гаммы, чтобы не менять гамму рабочего стола; в полноэкранном режиме `game.dll` задаёт показатель `1,2 − gamma/100` (измерено: 0 → 1,2, 30 → 0,9, 100 → 0,2). Runtime применяет тот же показатель перед таблицей дисплея, если значение передано в `graphicsSettings` или игра записала его в реестр. Без них вывод не меняется. Координаты мыши отображаются на пиксели экрана округлением вниз и, как курсор Windows, не выходят за пределы экрана: правый и нижний края — последние столбец и строка, где игра начинает прокрутку карты. Workers исполняют гостевые потоки с отдельными CPU/TEB/TLS. Broker обслуживает блокирующие ожидания и вложенные callbacks; его heartbeat позволяет законному INFINITE wait длиться дольше транспортного таймаута. SEH/C++ exceptions остаются неполными.

После `DLL_THREAD_DETACH` Worker публикует завершение и больше не обращается к WASM/shared memory. Broker сохраняет диагностический снимок и счётчики, освобождает CPU, native stack/TLS и guest stack/TEB, затем пробуждает ожидания. Handles продолжают хранить состояние и exit code завершённого потока. Лимит 16 применяется к живым Workers; в отчёте удерживаются последние 64 завершённых потока.

Критические секции хранят состояние в самой структуре `CRITICAL_SECTION`: `OwningThread` — атомарное слово блокировки, `RecursionCount`/`LockCount` обновляются владельцем, `LockSemaphore` считает ожидающих. Enter/TryEnter/Leave/Initialize/Delete исполняются в Worker без RPC; при конкуренции Worker ждёт через `Atomics.wait`, broker — через `Atomics.waitAsync` с отменой при остановке. Секции по невыровненному адресу (Warcraft размещает такие в упакованных структурах) остаются объектами broker. `qsort` также исполняется в Worker и вызывает компаратор гостя на его CPU.

`thread-state.mjs` хранит last-error и значения TLS в SharedArrayBuffer конкретного потока, а выделенные индексы — в общем реестре процесса. Get/SetLastError и TlsGet/SetValue выполняются локально в Worker; broker и отложенные операции используют те же ячейки. TlsAlloc/Free остаются в broker, допускают повторное выделение и обнуляют значения всех потоков. Предел 1088 и семантика обнуления сверены с [Microsoft TLS](https://learn.microsoft.com/en-us/windows/win32/procthread/thread-local-storage) и [TlsAlloc](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-tlsalloc); успешный [TlsGetValue](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-tlsgetvalue) сбрасывает last-error.

Backend `getError` выполняется на границах кадра, при строгом `glFinish` и чтении пикселей; подробный режим сохраняется для отладки. Аргументы и неподдерживаемые состояния проверяются сразу. Это устраняет лишние синхронные обращения к GPU-процессу, описанные в [WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices#avoid_blocking_api_calls_in_production), и не скрывает ошибки backend. `glFinish` по умолчанию лишь отправляет команды (`gl.flush()`): порядок относительно чтения пикселей гарантирует WebGL, задержку ограничивает темп кадров потока команд.

## Ресурсы и сохранения

`GET /api/assets` возвращает `{files:[{id,path,size,downloadUrl}]}`. Asset ID — SHA-256 пути, а не содержимого. `GET /api/assets/{id}` поддерживает один HTTP byte range. `GET /api/maps` возвращает SHA-256 содержимого, размер и доступные метаданные карты; `/api/maps/{id}/download` поддерживает Range/HEAD. Чтение не следует по symlink. Сервер не принимает файлы через эти API.

У каждой карты в `GET /api/maps` есть `header` — base64 первых 512 байт файла. При запуске Warcraft читает 124-байтный заголовок HM3W каждой карты для своих списков, и runtime отвечает на такие чтения из каталога, не скачивая блок 256 KiB на карту (163 карты — 30,5 МБ). Worker читает игровые ресурсы через синхронный Range XHR внутри Worker, блоками по 256 KiB; cache ограничен 64 блоками. Обрыв соединения, неполный блок, таймаут 30 с, 408, 429 и 5xx повторяются с паузами 0,25–4 с, всего 11 попыток (~28 с, `range-request.mjs`); другой ответ — ошибка сразу. Блок, которого нет ни в памяти, ни на устройстве, для `ReadFile` гостевого потока приходит через `fetch` (`game-files.mjs`, `readFileLater`): ждёт только этот поток, broker тем временем обслуживает остальные. `WarcraftHost.importMayWait` верен, пока выполняется import из `invokeAsync`. Гостевой код, который broker выполняет сам (`call`), читает синхронно. Поток, читающий файл подряд, получает в одном запросе до 4 блоков, каждый по мере прихода байтов, если по последним запросам время до первого байта больше передачи блока (`MAX_WINDOW`). Отчёт сессии содержит `gameData: {blocks, bytes, requests, stoodMs, backgroundMs, longestMs, longestPath, firstByteMs, blockMs}`, журнал — его итоговую строку. MPQ читается гостевым кодом через host filesystem, а не целиком передаётся браузеру заранее. Файл выбранной карты доступен по тому же интерфейсу. Хеш карты есть в каталоге, но при монтировании Worker пока не сверяет целиком её содержимое.

Гостевой файловый слой имеет изменяемый overlay. Перед стартом файлы SaveStore помещаются в overlay. Раз в секунду Worker передаёт изменённые файлы и удаления; открытые для записи файлы откладываются до CloseHandle, чтобы не сохранять незавершённый MPQ. При остановке такие файлы также пропускаются и перечисляются в `deferredSaveFiles`; main thread последовательно записывает пакеты в IndexedDB. При `finished` повторно передаётся весь overlay и список удалений. Ошибка записи отражается в статусе и итоговом `persistenceError`. Резкое закрытие страницы не гарантирует завершение последней транзакции. Оригинальное сохранение первой главы `.w3z` размером 1 944 590 байт создано игрой и загружено после полного перезапуска Chromium; использовалась штатная остановка runtime.

Снимки экрана (папка `Screenshots/`) в сохранения не попадают. Готовый снимок, уже закрытый игрой, Worker раз в секунду и при остановке отправляет странице сообщением `screenshot` и убирает из overlay. Снимок 1280×960 весит около 5 МБ, и десятки таких файлов исчерпали бы лимит сохранений в 128 МБ. Снимки из старых сохранений в overlay не загружаются.

IndexedDB: база `wc3-web-saves`, store `files`. Пути относительные POSIX без `..`. Экспорт `wc3-web-saves-v1` включает base64, SHA-256 и timestamp; импорт сначала проверяет архив и записывает его транзакцией. Лимиты: 32 MiB на файл, 128 MiB и 4096 файлов всего. Данные привязаны к origin и профилю браузера.

Сервер отдаёт COOP `same-origin` и COEP `require-corp`. Внешнему серверу нужен HTTPS; localhost подходит для разработки.

## Сетевой транспорт и Winsock

**Данные игры на устройстве** (`game-cache.mjs`). Архивы, исполняемые файлы и карты кэшируются в OPFS блоками по 256 КиБ; ролики не кэшируются, их проигрывает `<video>`. Страница загружает ролик до трёх раз (третий — с сервера). Ролик, который так и не загрузился, DirectShow завершает сразу (`EC_COMPLETE`, в журнале `Cinematic skipped`). У каждого ассета есть `version` — SHA-256 от размера и времени изменения, у карты — SHA-256 содержимого. Файл с другой версией скачивается заново, прежний удаляется. Один OPFS-файл соответствует одной версии ассета, `index.json` хранит битовые карты блоков. Worker читает блоки синхронно (`FileSystemSyncAccessHandle`) и сохраняет блоки, скачанные с сервера. Хранилищем одновременно владеет одна сессия (Web Lock `wc3-game-data`): вторая вкладка с игрой или предзагрузкой работает через сеть. Для страницы `client.mjs` экспортирует `gameDataStatus({language})`, `preloadGameData({language, onProgress})` → `{done, cancel}` (отдельный Worker, диапазоны до 8 МиБ, `navigator.storage.persist()`) и `deleteGameData()`. Страница считает только архивы и исполняемые файлы языка и не загружает каталог карт. Статические файлы (страница, runtime, `wc3.wasm` ~180 МБ) отдаются с `ETag`, поэтому повторный запуск получает `304` вместо новой загрузки.

**Первый запуск** (`prepareGame({wasmUrl, wasmSize, language, onProgress, onStatus})` → `{done, cancel}`). До старта игры лаунчер скачивает то, что она читает до главного меню. Список берётся из `var/runtime/boot-<language>.json` (`make boot-set`, `tools/record_boot_set.py`): `{schemaVersion:1, language, files:[{path, size, whole:true} | {path, size, blocks:[[first,last],…]}], media:[путь ролика]}`. Его записывает чистый профиль Chromium, дошедший до меню с настройками лаунчера по умолчанию. Исполняемые файлы приходят целиком одним запросом (gzip), блоки архивов — диапазонами до 8 МиБ, ролик — целиком; в Worker `game-cache-worker.mjs` (`prepare`) идёт до шести загрузок сразу, всё попадает в OPFS. Модуль WebAssembly скачивается в HTTP-кэш браузера. Если там уже есть копия с текущим `ETag` (`cache:'only-if-cached'` и `HEAD`), его не скачивают. Runtime Worker потом подтверждает кэш запросом с проверкой. Файл другого размера, чем при записи, пропускается. Без списка скачиваются только исполняемые файлы из `build.json`. `onProgress({done,total})` передаёт байты в сети; для gzip — сжатые. Итог появляется, когда обе части знают свой размер, поэтому полоса не идёт назад. `done` даёт `{cancelled, media, release()}`: `media` — URL копий роликов для `runDiagnostics`, `release` освобождает их. Ошибки загрузки не мешают запуску, они уходят в `onStatus`. Замер на 32 Мбит/с с задержкой 50 мс: 71 МБ за ~18 с, затем меню через 4,3 с после пропуска ролика, без данных с сервера. Раньше меню ждало 12,4 с и ещё качало заголовки карт. Повторный запуск ничего не скачивает.

**Сжатие** (`server/compression.py`). Файл целиком (без `Range`) с расширением `.wasm`, `.mjs`, `.js`, `.css`, `.html`, `.json`, `.svg`, `.txt`, `.exe` или `.dll` размером от 1 КиБ уходит с `Content-Encoding: gzip`, если `Accept-Encoding` допускает gzip. Браузер распаковывает его сам, поэтому страница и Worker получают исходные байты; SHA-256 модулей игры проверяется после распаковки. Выбран gzip: его понимают все браузеры, по HTTP и HTTPS (brotli браузеры предлагают только по HTTPS, zstd — только новые). Ответ несёт `Vary: Accept-Encoding` и собственный `ETag` с суффиксом `-gzip`; `If-None-Match` с ним даёт `304`. Запросы с `Range` и несжимаемые файлы (MPQ, карты, WebM: gzip уменьшает их примерно на 2%) отдаются как есть. Каждая версия файла (устройство, inode, размер, время изменения) сжимается один раз уровнем 9 в потоке и хранится в памяти (лимит 256 МБ; runtime, исполняемые файлы и скрипты занимают около 25 МБ). Одновременные запросы ждут одно сжатие; файл, сжатый меньше чем на 10%, отдаётся без сжатия. `wc3.wasm` сжимается при запуске сервера: 118 МБ → 11,8 МБ (до маски окна гостя было 175 → 19,2 МБ, около 10 с). `game.dll` — 11,5 → 3,8 МБ.

`GET /api/assets?language=en` возвращает файлы базовой установки, в которых локализованные файлы из `var/locales/en` (`tools/prepare_locale.py`) заменяют базовые с теми же путями. У заменённых файлов собственные ID (SHA-256 от `locales/en/<путь>`), поэтому оба языка можно скачивать одновременно. Незнакомый язык возвращает 400. Кроме архивов локализация может содержать отдельные файлы игры (английская — `Fonts/FRIZQT__.TTF` с кириллицей, `tools/prepare_fonts.py`; `locale.json` перечисляет их в `localFiles`). Если среди файлов запуска есть `Fonts/…`, runtime записывает в реестр `Allow Local Files = 1`, и Warcraft читает такие файлы раньше архивов. `GET /api/status` перечисляет доступные языки в `game.languages`: сначала базовый (`--base-language`, по умолчанию `ru`), затем подготовленные; неполная локализация (без `locale.json` или одного из четырёх архивов) не предлагается.

`GET /api/lobbies` возвращает `{lobbies:[{id,name,players,maxPlayers}],maxPlayers}`. `POST /api/lobbies` с JSON `{name}` создаёт публичное лобби; имя содержит 1–48 символов. Незанятое созданное лобби истекает через 120 секунд, после выхода последнего участника комната удаляется. Частные коды не публикуются в списке.

Страница при закрытии (`pagehide`) сама закрывает соединения лобби и счётчика: место и счётчики освобождаются сразу. Соединение пропавшей страницы сервер закрывает по ping: у relay heartbeat 10 секунд, у счётчика 15, ответа ждут половину интервала.

`GET /api/locale` возвращает `{language:"ru"|"en"|null}`, `Cache-Control: no-store`: язык страницы по умолчанию для посетителя, ещё не выбравшего язык. `ru` возвращается для стран СНГ (`RUSSIAN_COUNTRIES` в `server/geoip.py`), `en` для остальных, `null` для неизвестной страны: нет базы, адрес локальный или частный. Страница тогда берёт язык браузера. Если запрос пришёл с loopback- или частного адреса (обратный прокси), адресом посетителя считается последняя запись `X-Forwarded-For`, а заголовок `CF-IPCountry` (кроме `XX`, `T1`) имеет приоритет. База — DB-IP Country Lite (`--geoip`, по умолчанию `var/geoip/dbip-country-lite.csv.gz`, `make geoip`). В памяти держатся только диапазоны стран СНГ, около 20 000 после слияния; загрузка занимает 0,3 с в фоновом потоке. Файл перечитывается при изменении, проверка раз в шесть часов. Пока страница ждёт ответа (не дольше 1,5 с), её содержимое скрыто атрибутом `data-pending-language`; без скриптов оно появляется через 2 с.

`WebSocket /api/presence` — анонимные счётчики панели «Сейчас играют» и живой список лобби. Страница отправляет JSON `{playing, lan, presenceToken}`. Токен выдаётся только владельцу relay-соединения в `welcome`, действует до его закрытия и не является постоянным идентификатором посетителя. `lan` считает уникальные действующие токены страниц с запущенной игрой: устаревший флаг без relay-соединения не учитывается, повторное использование места в лобби получает новый токен. При изменении состава лобби relay также уведомляет presence. Не чаще раза в секунду сервер рассылает единый снимок `{type:"presence",online,playing,lan,lobbies,maxPlayers,privatePlayers}`. `lobbies` содержит публичные комнаты; для комнат по коду передаётся только общее число участников `privatePlayers`, без кодов и токенов. Страница обновляет список и счётчики вместе, игнорируя более старые HTTP-ответы; `GET /api/lobbies` остаётся для ручного обновления и возвращает тот же состав лобби. Закрытие relay немедленно исключает его токен из LAN, даже если presence-соединение остаётся открытым; таймаут heartbeat relay удаляет исчезнувшее соединение. `GET /api/status` возвращает три счётчика в поле `presence`. Ограничения: тот же Origin, входящее сообщение до 256 байт, не больше 20 сообщений за 10 секунд, ping каждые 15 секунд. За обратным прокси все посетители имеют один адрес, поэтому ограничено только общее число соединений presence (4096); счётчики не влияют на допуск в лобби.

`WebSocket /api/relay/{room}?lobby=1` входит в существующее публичное лобби; без query сохраняется поддержка частного кода из 8–64 символов `[A-Za-z0-9_-]`. В комнате до 200 участников (ID 1–200, виртуальные адреса `10.77.0.1–200`; формат кадра допускает до 254), в процессе до 256 комнат. Общие лобби каждого языка (`shared-en-1`, `shared-en-2`, `shared-ru-1`, `shared-ru-2`) существуют всегда. `WebSocket /api/relay/auto?language=en|ru` выбирает первое общее лобби этого языка со свободным местом по возрастанию номера, а если все заняты — создаёт дополнительное с наименьшим свободным номером (`shared-ru-3`, …). Номера проверяются по возрастанию, поэтому сначала заполняются постоянные лобби 1–2, затем уже открытые дополнительные, и только потом открывается новое. Дополнительное лобби удаляется, когда его покидает последний участник. Созданные игроками лобби `auto` не заполняет. Без `language` используется язык базовой установки (`ru`), незнакомый язык возвращает 400. Созданные игроками лобби языка не имеют. Выбор и резервирование места выполняются без ожидания между ними, поэтому два одновременных подключения не займут последнее место дважды. `welcome` сообщает выбранную комнату (`room`) и её `lobby` (`shared` — номер общего лобби, `language` — его язык, `maxPlayers` — вместимость). `GET /api/lobbies` перечисляет сначала общие лобби по языкам (English, затем Русский: латиница A–Z, потом кириллица А–Я) и номерам, затем созданные пользователями; перезапуск сервера разрывает соединения. FrameTransport кэширует `peerIds`: runtime получает состав уже занятого лобби при запуске, затем все изменения.

Управляющие сообщения — JSON `{type:"welcome",peerId,room,protocol:"wc3-frame-relay-v1",peers,lobby}` и `{type:"peers",peers:[...]}`. ID назначает сервер (наименьший свободный). Бинарный клиентский кадр начинается байтом destination (0 = broadcast), затем содержит 1–65535 байт payload. Сервер заменяет первый байт на настоящий source ID и передаёт пакет только адресатам той же комнаты; собственный broadcast не возвращается. Есть ограничения размера, очередей и частоты.

`VirtualWinsock` реализует поверх FrameTransport виртуальные UDP и TCP: порты, bind/listen/connect/accept, очереди receive, select readiness, handshake, stream fragmentation и FIN/RST. Адреса peers — `10.77.0.1`…`10.77.0.12`. Отсутствие данных возвращает `WSAEWOULDBLOCK`; это неблокирующая модель, не полноценные сокеты ОС. Platform-слой маршалит WSOCK32 ordinals, sockaddr/fd_set и ошибки из guest memory.

Payload виртуального сокета начинается 16-байтным заголовком `CWS1`: type (u8), reserved (u8), source port (u16), destination port (u16), payload length (u16), connection ID (u32). Все многобайтные поля little-endian; UDP использует connection ID 0. Надёжность и порядок кадров обеспечивает WebSocket, а не настоящий TCP/IP браузера.

Типы пакетов: UDP 1, SYN 2, SYN_ACK 3, ACK 4, DATA 5, FIN 6, RST 7, GONE 8. GONE состоит из одного заголовка: порты, длина и connection ID нулевые. `client.mjs` рассылает его всем (destination 0), когда на этом соединении с лобби начинается игровая сессия и когда она заканчивается остановкой, ошибкой или падением runtime. Получатель сбрасывает свои TCP-соединения с отправителем, как Windows сбрасывает соединения завершённого процесса:

- установленное соединение получает `WSAECONNRESET` и остаётся readable, поэтому select и ожидающие операции просыпаются;
- устанавливаемое соединение получает `WSAECONNREFUSED`;
- ещё не принятое соединение удаляется.

Соединения с другими участниками не затрагиваются. Без GONE страница, у которой упала игра, оставалась в комнате, и Warcraft остальных ждал её около 50 секунд. Уход участника из комнаты (сообщение `peers`) тоже сбрасывает соединения с ним (`WSAECONNRESET`). Потеря собственного соединения с лобби даёт всем TCP-соединениям `WSAENETDOWN`.

`mswsock.dll!AcceptEx` принимает соединение в заранее созданный сокет; `GetAcceptExSockaddrs` возвращает адреса из его буфера. `WSARecv` и `WSASend` поддерживают WSABUF и OVERLAPPED с событиями или completion ports. Ожидание возвращает WSA_IO_PENDING, пакет будит настоящий гостевой поток через GetQueuedCompletionStatus; закрытие сокета отменяет ожидающий ввод-вывод. Временные WSABUF захватываются до возврата в игру. APC completion routines пока не реализованы. `WSAIoctl` поддерживает запрос указателей этих расширений, FIONREAD/FIONBIO и используемое Warcraft отключение UDP ICMP reset.

Без relay создаётся отдельный loopback `127.0.0.1` для локальной инициализации Winsock и UDP/TCP внутри одного runtime. Он не связывает браузеры; удалённые адреса недоступны. Блокирующий select и асинхронные операции интегрированы с планировщиком гостевых потоков. Компонентные тесты обмена не заменяют проверку Warcraft LAN-матча.

Warcraft discovery, host/join, загрузка Echo Isles, команды рабочих, добыча ресурсов, бой/смерть юнита и отключение второго игрока проверены двумя процессами Chromium. Сообщений о рассинхронизации в этом прогоне не было. Длительная синхронность и другие карты ещё не проверены. Транспорт не синхронизирует игровой мир и не реализует Battle.net.

# Анализ nfsu2-web и перенос на Warcraft III

Исследована локальная копия [th0mk/nfsu2-web](https://github.com/th0mk/nfsu2-web), commit [`3e61f9c37cb7ce4084dde182047c1b782bd9ac1a`](https://github.com/th0mk/nfsu2-web/tree/3e61f9c37cb7ce4084dde182047c1b782bd9ac1a), 5 ноября 2026 года. Ниже перечислены свойства прочитанного исходного кода, а не результаты запуска Warcraft в этом runtime.

**Вывод:** в nfsu2-web действительно исполняется оригинальный машинный код игры, заранее переведённый в C и скомпилированный в WebAssembly. Это специализированный порт NFS Underground 2, а не универсальный загрузчик Windows EXE. Замена имени `SPEED2.EXE` на `war3.exe` не создаёт порт Warcraft. Сервер карт, веб-интерфейс и сетевой ретранслятор также не заменяют исполняющий игру runtime.

## Как устроен оригинальный проект

```text
SPEED2.EXE + server.dll
        │ PE-анализ, функции, relocation, инструкции x86
        ▼
tools/lift.py + tools/genall.py
        │ C-код функций + таблицы dispatch/import
        ▼
gen/all + gen/server + runtime/*.c + runtime/web/*.c
        │ wasi-sdk, wasm32-wasip1-threads
        ▼
nfsu2.wasm
        │ общая WebAssembly.Memory
        ├── workers: потоки игры и Win32 HLE
        ├── I/O worker: HTTP game data + локальные сохранения
        ├── WebGPU: команды D3D9
        ├── AudioWorklet: PCM
        └── сетевой worker: WebSocket ↔ виртуальная LAN

Rust-сервер: страница, WASM, игровые файлы, LAN relay
```

Сервер не запускает Windows-игру и не передаёт видеопоток. Вычисления игры выполняет браузер каждого игрока. Каталог игры остаётся на сервере; клиент получает нужные данные по HTTP.

### Генерация и сборка

- `gen.sh`: получает relocation, строит набор функций, генерирует C, определяет ABI импортов; отдельно подготавливает и переводит `server.dll`.
- `web/gen.sh`: включает оптимизации FLAGABI, X87OPT, JTSWITCH, LREGS, FTOL2INL и список горячих функций. Контролирует число `lift-error`, но успешная генерация сама по себе не доказывает корректное исполнение игры.
- `tools/genall.py`: находит функции от точки входа, дополнительных seeds, relocation-указателей и вызовов; создаёт C shards, таблицу адресов и заглушки для непереведённых участков.
- `tools/lift.py`: переводит инструкции x86-32, моделируя регистры, флаги, x87 и SIMD в структуре `CPU`.
- `tools/prepare_module.py`: переносит DLL на фиксированную базу, создаёт seeds из entry point/exports и записывает SHA-256 исходной DLL. Поддерживает relocations HIGHLOW.
- `tools/argcount.py`: строит таблицы импортов, комбинируя известные сигнатуры с анализом вызовов. Для дополнительной DLL есть строгий режим. Для нового набора импортов нельзя полагаться только на эвристики числа аргументов.
- `web/build.sh`: компилирует C с wasi-sdk, shared memory, SIMD, tail calls и обработкой исключений. Это собственный WASI host, не Emscripten. Сборка требует `gen/all` и `gen/server` и проверяет соответствие генерации текущим исходникам.

Линкер размещает runtime выше `0x28000000`, оставляя нижний диапазон памяти гостевой программе. Начальное выделение по умолчанию — 1024 MiB, максимум — 4 GiB. Эти параметры рассчитаны для NFS и не являются готовой схемой адресного пространства Warcraft.

### Выполнение в браузере

- `runtime/cpu.h`: машинное состояние, гостевая память, flags/FPU, быстрые переходы к переведённым функциям.
- `runtime/dispatch.c`: непрямые вызовы/переходы, HLE imports, дополнительные модули и runtime patches.
- `runtime/web/main_web.c`: загрузка PE, Win32/COM, TEB/PEB, гостевой стек, инициализация подсистем, запуск entry point.
- `web/src/host/process.ts`: общая `WebAssembly.Memory`, I/O worker и пул игровых workers. Для каждого гостевого потока исполняется тот же WASM-модуль с общей памятью.
- `web/src/host/game-worker.ts`, `abi.ts`, `proto.ts`: WASI-вызовы, блокирующий RPC, запуск потоков и интерфейс runtime с браузером.
- `runtime/web/host_abi.h`: регистрация GPU, AUDIO, INPUT, NET, STATUS, VSYNC и LAN через указатели на структуры в общей памяти.
- `web/src/app/checks.ts`: secure context, cross-origin isolation, SharedArrayBuffer, shared WASM memory, SIMD, Atomics.waitAsync и GPU adapter. Одного наличия WebAssembly недостаточно.

### Файлы и сохранения

- `web/server-rs/src/app/manifest.rs`: `/data-manifest`, строгий список допустимых игровых каталогов, исключение скрытых файлов и symlinks. Список содержит имена NFS (`cars`, `tracks`, `speed2.exe` и другие), его необходимо заменить для WC3.
- `web/server-rs/src/app/files.rs`: потоковая отдача файлов, HEAD, ETag, одиночные byte ranges, ответы 206/416.
- `web/server-rs/src/app/blocks.rs`: поблочная доставка игровых файлов.
- `web/src/host/io-worker.ts`, `datacache.ts`: HTTP-загрузка и кеш блоков, OPFS, лимиты открытых дескрипторов и обработка ошибок кеша.
- `runtime/fileio.c`: представление Windows-путей, read-only install root и отдельный write overlay.
- `web/src/app/savefs.ts`, `saves-ui.ts`, `vault.ts`: сохранения браузера, экспорт/импорт и облачное хранилище проекта.

Для Warcraft нужны MPQ-архивы и порядок их наложения, внешние `Maps`, `Campaigns`, профили, `Save`, `Replay` и соответствующие записи реестра. Наличие MPQ на HTTP-сервере не означает, что движок уже умеет читать его в WASM: это задача перенесённого Storm/runtime.

### Графика и звук

`runtime/com.c` реализует интерфейсы Direct3D **9**, DirectSound и DirectInput. `runtime/web/gpu_web.c` записывает команды от D3D9, `gpu_proto.h` описывает бинарный контракт, а `web/src/gpu/` отправляет команды WebGPU. В протоколе и шейдерах есть особенности NFS, включая фары и эффекты. В изученном runtime не найдена реализация `Direct3DCreate8` или WGL/OpenGL API, необходимая для соответствующих путей старого Warcraft.

`runtime/web/audio_web.c` рассчитан на то, что EA-микшер игры уже наполняет looping DirectSound buffer PCM-данными; браузерная часть воспроизводит их через AudioWorklet. Для WC3 нельзя считать этот слой реализацией Miles (`Mss32.dll`): библиотеку и её API требуется отдельно перенести, перевести либо заменить совместимой реализацией.

## Почему перенос не является заменой ресурсов

| Привязка NFS | Точное место | Что требуется Warcraft |
| --- | --- | --- |
| Relocation-таблица ищется в безымянной PE-секции | `tools/reloc2.py` | Стандартный PE relocation reader и проверка каждого EXE/DLL |
| Изменение операндов по адресам NFS | `tools/lift.py`, `tools/split_reloc.py` | Отключение NFS-патчей, профиль конкретных WC3-бинарников |
| `split_operand` вызывается для любого образа с базой `0x400000` | `tools/lift.py`, методы адресации и immediate operands | Не использовать базу образа как признак игры; иначе возможна тихая порча WC3-кода |
| Оптимизация `_ftol2` по адресу `0x0075bed4` | `tools/lift.py` | Отдельное определение функций/ABI Warcraft |
| Списки исключений и оптимизаций по адресам | `tools/retpast.txt`, `tools/inline_hot.txt` | Повторный анализ, а не перенос числовых адресов |
| Жёстко вызывается `sub_0075bcc7` | `runtime/web/main_web.c`, `guest_main_thread` | Entry point из WC3 PE и корректный путь запуска дополнения |
| Dispatch покрывает диапазон NFS `.text` | `runtime/cpu.h`: `DISPATCH_TEXT_BASE=0x00401000`, `DISPATCH_TEXT_SIZE=0x00381af1` | Таблицы всех исполняемых секций и модулей WC3 |
| Loader дополнительных DLL содержит один `server.dll` | `runtime/module.c`: `g_mods[1]` | Многомодульный loader: WC3 launcher/engine/Storm/Miles и фактические зависимости |
| Реализован COM D3D9 | `runtime/com.c` | Совместимый D3D8 или OpenGL backend, в зависимости от выбранного пути Warcraft |
| Инициализация патчей карьеры, машин, гаража, локализации NFS | `runtime/web/main_web.c`, `runtime/overrides.c` и связанные файлы | Удаление чужих hooks и отдельная интеграция WC3 |
| Сетевые надстройки EA и free roam | `runtime/online.c`, `roam*.c`, `racenet.c` | Сетевой протокол WC3 и сохранение его детерминизма |

Таким образом, даже если из `game.dll` успешно получить большой набор C-функций и связать WASM, это ещё не подтверждает загрузку меню, миссии, аудио, сохранений или матча.

## Что можно переиспользовать

1. Общую архитектуру x86 → C → WASM и часть lifter после удаления NFS-профиля. Нужны тесты инструкций и дифференциальные проверки с исполнением исходного WC3 на Windows.
2. Архитектуру shared-memory workers, WASI RPC, кольцевые буферы и проверки соответствия ABI между C и TypeScript.
3. HTTP Range, серверный manifest, OPFS cache и write overlay. Для больших MPQ важна загрузка диапазонов вместо полной предварительной загрузки всей установки.
4. Браузерные события ввода, AudioWorklet-выход PCM и элементы WebGPU renderer, когда новый графический backend предоставит совместимые команды.
5. Виртуальный LAN-коммутатор как транспорт, после отделения интерфейсов NFS.
6. Подход к HTTPS, cross-origin isolation, проверкам сборки, ограничениям очередей, путям и наблюдаемости.

Репозиторий распространяется под MIT; при копировании кода нужно сохранять его `LICENSE` и уведомления об авторстве. Генерируемый код/WASM происходит из пользовательских игровых бинарников и в оригинальном проекте не коммитится. В этом проекте игровые архивы и производные артефакты также следует держать отдельно от исходников приложения.

## Мультиплеер: транспорт и игра — разные слои

В оригинале `runtime/winsock.c` реализует Windows socket semantics, а `runtime/web/net_lan.c` переводит их в виртуальные UDP/TCP/ICMP сообщения. Через shared-memory rings и `web/src/net/worker.ts` они уходят WebSocket-соединением в Rust-коммутатор `web/server-rs/crates/lan`. Коммутатор маршрутизирует сообщения по виртуальным адресам; логика матча остаётся в игре.

Протокол описан непосредственно в `crates/lan/src/lib.rs`: бинарные сообщения имеют kind, source/destination IPv4 и payload, а JSON-сообщения обслуживают hello, адреса, peers и ping. Источник пакета переписывается сервером, есть лимиты, очереди, отключение медленных клиентов и возобновление владения адресом по токену. TCP-сегменты идут поверх надёжного WebSocket; произвольного доступа браузера к реальным UDP/TCP-сокетам нет.

Для WC3 нужно перенести настоящий Winsock-вызов игры в этот транспорт, обеспечить LAN discovery, соединение хоста с участниками, передачу/проверку карты и игровой lockstep. Самостоятельная веб-комната с чатом или пересылкой JSON ещё не является работающим мультиплеером Warcraft. Протокол free roam NFS нельзя использовать вместо протокола WC3. Совместимость с Battle.net из реализации LAN не следует и отдельно не подтверждена.

## Проверяемые этапы готовности

| Этап | Критерий, который должен пройти |
| --- | --- |
| Идентификация установки | SHA-256, PE version/resources, imports/exports/relocations всех задействованных модулей; версия подтверждается содержимым, а не именем ZIP |
| Выполнение | Entry point WC3 действительно исполняется; нет ложных успешных ответов на отсутствующие критические API |
| Меню | Оригинальное меню TFT, мышь/клавиатура, отрисовка и звук работают в браузере |
| Одиночная игра | Штатная карта загружается; работают юниты, AI, ресурсы, победа/поражение |
| Кампания | Миссия TFT, заставки/озвучка, сохранение/загрузка и переход между миссиями проверены |
| Карты сервера | Новая `.w3m`/`.w3x` появляется в каталоге и доступна движку; одинаковые байты/хеш у участников |
| Сеть | Два независимых браузера находят LAN-игру, входят и играют один матч без рассинхронизации; проверены выход и разрыв связи |
| Регрессии | Проверены перезагрузка страницы, сохранения, кеш, большие MPQ и ошибки сети |

Загрузка страницы, выдача списка карт, синхронизация комнаты и успешная генерация C являются полезными самостоятельными проверками инфраструктуры. Они не должны обозначаться как завершённый игровой порт до прохождения соответствующих этапов выше.

## Повторная сверка интерфейса и вывода графики — 6 ноября 2026

Проверены живая страница [nfsu2.xyz](https://nfsu2.xyz/), её HTML/CSS и текущие `web/src/main.ts`, `web/src/app/display.ts`, `web/src/app/shell.ts` upstream. Для WC3 воспроизведены компактная двухколоночная структура, левая карточка Play, вкладки, контурные кнопки, акцентная полоса и полноэкранная обёртка с отключением фонового интерфейса. Палитра изменена на сине-голубую; Donate, придуманный логотип и выбор карт в браузере удалены. Discord оставлен с пустой ссылкой.

Повторно прочитаны `runtime/web/gpu_web.c`, `gpu_proto.h` и `web/src/host/game-worker.ts`: NFS записывает кадры/ресурсы в shared memory и синхронизирует передачу renderer. Для Warcraft реализована своя ограниченная очередь OpenGL-состояния в SharedArrayBuffer; матрицы и векторы копируются на момент вызова, draw/query/upload и прочие брокерные операции исполняют её по порядку. Это тот же принцип уменьшения межпоточных ожиданий; конкретные графические протоколы различаются (у WC3 OpenGL → WebGL2, у текущего NFS — WebGPU). Адресные патчи и игровые протоколы NFS в Warcraft не применяются.

# Перевод PE32 в C

## Глубокие виртуальные вызовы

`tools/build_runtime.py` применяет `self_call_source` к компилируемой копии
шардов в обеих сборках. Для функций с состоянием в CPU/гостевой памяти,
только косвенными вызовами и обычными `RET` вызов того же адреса входа
становится переходом к началу функции. Адрес возврата, аргументы и сохранённые
регистры остаются на гостевом стеке; `RET` выполняет исходные `POP` и очистку
аргументов, затем переходит к продолжению вызывающей инструкции. Счётчик
вложенности локален для каждого настоящего вызова C, поэтому отдельный вход
из host callback не путается с уже выполняющимся обходом.

Перед этим проходом сборщик встраивает маленькие виртуальные обходы в
обёртки C++-деструкторов, проверяющие младший бит аргумента удаления. Это
обычное встраивание исходных инструкций на один уровень: освобождение объектов,
регистрация SEH, стековые операции и другие вызовы сохраняются. Для каждой
обёртки допустим ровно один вызов встраиваемого обхода; размеры обеих функций
ограничены. Так рекурсивный вызов через тело деструктора становится виден
основному проходу, без переписывания логики удаления дерева.

Вызовы других адресов сохраняют обычный dispatch, включая совместимый
трамплин хвостовых переходов. Trace и dispatch budget проверяются и на
оптимизированных вызовах. Функции с локальными регистрами, хвостовыми выходами
или неизвестной формой `CALL`/`RET` остаются без изменений. Прямые вызовы
допускаются только во встроенных обёртках; остальные функции с ними пропускаются.
Оптимизация не зависит от адресов Warcraft или названий карт; она не устраняет
произвольную взаимную рекурсию разных функций. Исходные сгенерированные шарды
не меняются; хеш преобразованного текста (включая тело из другого шарда) и
версия прохода входят в ключ object cache, версия — в проверку соответствия
обычной и совместимой сборок.

`tests/test_runtime_self_calls.py` собирает независимый синтетический обход
дерева, с обёрткой и без неё: исходный вариант воспроизводит переполнение браузерного стека,
исправленные варианты проходят 30 000 уровней с обеими ветвями дерева,
вложенным входом из host, проверкой порядка обхода, баланса стеков и бюджета.
Фикстура не содержит кода или данных игры.

## Генерация и сборка

`tools/lift_wc3.py` читает настоящий PE32 EXE/DLL и генерирует C из инструкций x86 через закреплённую версию lifter из nfsu2-web. В `runtime/` есть CPU helpers, PE loader и dispatch; `tools/build_runtime.py` собирает их вместе с переведёнными модулями в настоящий WASM. Наличие WASM пока не подтверждает работу кампании или мультиплеера.

Установка зависимостей и короткая проверка:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python tools/lift_wc3.py \
  --image var/game/game.dll \
  --output var/lift/game-smoke \
  --max-functions 32
```

Каталог результата должен быть новым или пустым: команда не удаляет прежнюю генерацию. `--max-functions 0` обходит все кандидаты, `--functions-per-shard 64` задаёт размер C-файлов. `--strict` возвращает ненулевой код при ошибках перевода, unsupported-инструкциях, обрезанных/пустых блоках и инструкциях, требующих проверки семантики. Даже успешный strict-run не подтверждает исполнение или корректность игры.

```sh
.venv/bin/python tools/lift_wc3.py \
  --image var/game/game.dll \
  --output var/lift/game-full \
  --max-functions 0

.venv/bin/python -m unittest discover -s tests -p test_lift_wc3.py -v
```

В результате появляются `shard_*.c`, `decls.h`, `fntab.c`, `report.json` и `progress.json`. Файлы используют отдельный CPU header `runtime/cpu.h`; таблицы имеют префикс модуля (`wc3_game_count/address/function`), а функции — адресные имена `sub_6f...`. `--module` позволяет явно выбрать префикс. Пересекающиеся адреса разных модулей запрещены при сборке: такой модуль сначала нужно корректно релокировать и перевести заново. C-код и отчёты, производные от игрового бинарника, записываются в игнорируемый каталог `var/`.

Генератор начинает с PE entry point, exports и адресов из стандартных HIGHLOW relocations, затем добавляет цели прямых вызовов. Он рассматривает все исполняемые PE-секции, включая `MSSMIXER`, с ограничением общего адресного span в 256 MiB. Relocation-указатель может вести к блоку внутри функции или данным. Поэтому `attempted_functions`/`generated_functions` являются счётчиками кандидатов, а не доказанным числом исходных функций. `static_coverage` измеряет декодированные байты, а не покрытие исполнения. Недостижимые указатели, jump tables и границы функций потребуют дальнейшего анализа.

Для EXE без HIGHLOW relocations режим `--scan-data-pointers auto` дополнительно сканирует выровненные 32-bit значения в неисполняемых initialized/readable секциях. Только значения внутри исполняемых диапазонов становятся seeds с origin `data_pointer`; проверенные секции и пары slot→target записываются в отчёт. Это необходимо для CRT initializer callbacks: при реальном boot `war3.exe` вызвал через `_initterm_e` адрес `0x00403524`, который хранится в `.rdata` по `0x00456ae8`, но отсутствует в relocation metadata. Универсальный сканер восстановил этот callback без патча по конкретному адресу. Режимы `always` и `never` позволяют явно изменить политику. Указатели из данных остаются кандидатами и могут давать ложные границы функций.

Режим `--scan-code-pointers auto` при отсутствии HIGHLOW relocations также добавляет адреса из уже декодированных `PUSH`/`MOV` с 32-bit immediate и `LEA` с абсолютным адресом. Обход продолжается до исчерпания новых кандидатов, включая callbacks внутри вновь найденных функций. Origin `code_pointer` и пары instruction→target сохраняются отдельно в `code_pointer_scan`. Это восстановило конструктор `0x00449540`: игра передаёт его через `push` по `0x0044a0e1` в CRT array-constructor helper. Сырые байты `.text` и произвольные арифметические константы не сканируются; указатели, вычисляемые несколькими инструкциями, пока не разрешаются. Режимы `always`/`never` позволяют явно управлять этим проходом.

NFS-патчи явно отключены: переписывание операндов split-screen, список `retpast`, `_ftol2` по фиксированному адресу, hooks и оптимизации с адресными списками. Для первого анализа также выключены агрессивные оптимизации флагов/регистров. Оригинальные файлы vendored-копии не изменяются; хеши закреплены в `vendor/nfsu2/provenance.json`.

## Второй проход и WASM runtime

После первого прохода добавлены:

- CPU header с неизменённой структурой `CPU`, адресуемой через `g_mem` памятью и checked unaligned/alias-safe доступом. Жёсткие NFS-адреса и зависимости split-screen удалены.
- Карта доступа к памяти: один бит на 4 KiB страницу, `1` — RW, `0` — NOACCESS. В диагностической сборке (`-DWC3_STRICT_MEMORY=1`, `build_runtime.py --strict-memory`) `wc3_mem_ptr` проверяет каждую затронутую страницу, а атомарные операции проходят тот же контроль; сборка по умолчанию проверяет в гостевом коде только границы (см. ниже). Хост и `VirtualAlloc`/`VirtualProtect` используют карту всегда. Это позволяет отличать `MEM_RESERVE` от последующего `MEM_COMMIT`. Чтение или запись зарезервированной страницы вызывает fault; commit восстанавливает доступ. Режим read-only не имитируется через C lvalue.
- `LOCK` ADD/ADC/SUB/SBB, логические операции, INC/DEC/NEG/NOT, XADD/XCHG, CMPXCHG/CMPXCHG8B и bit operations через последовательные C atomics. Невыровненные atomic operands явно вызывают fault; обычные unaligned обращения поддерживаются. Параллельное исполнение остальных гостевых инструкций требует сериализации runtime.
- Исправление направления сравнения флагов CMPXCHG: ACC − DEST.
- Явные ошибки на far pointers, privileged instructions, пустых и достигших лимита блоках. Прежние шесть `KeyError: 6` заменены диагностируемыми fault paths, а не выдуманной поддержкой сегментных переходов.
- Отдельная диагностика подозрительных code/data candidates. Они остаются в таблицах с traps; генератор не отбрасывает их молча.
- Отдельные CPU/TEB/stack contexts для shared-memory Workers, thread notifications DLL и восстановление после исключений host. ABI и проверка настоящими параллельными WASM instances описаны в [runtime-threads.md](runtime-threads.md).

| Модуль | Сгенерированные кандидаты | Ошибки генерации | Unsupported/trap sites |
| --- | ---: | ---: | ---: |
| `war3.exe`, включая data/code-pointer callbacks | 2 630 | 0 | 20 |
| `game.dll` | 82 072 | 0 | 5 909 |
| `Storm.dll` | 1 520 | 0 | 84 |
| `ijl15.dll` | 743 | 0 | 168 |
| `Mss32.dll` — отдельно исследован, не включён в текущую сборку | 1 619 | 0 | 107 |

Рост trap sites относительно первого прохода означает, что операции, которые upstream молча пропускал как якобы данные, теперь прекращают исполнение с диагностикой. Например, `outsd` встречается 3 244 раза в статически декодированном наборе `game.dll`. Это не доказательство того, что реальная игра исполняет эти инструкции. Обнаружено 857 кандидатов с признаками privileged/ошибочного data decoding, 68 пустых блоков и один достигший лимита; пустые и ограниченные блоки теперь также явно вызывают fault.

Полное сохранение/восстановление x87 environment пока не реализовано: исходная структура `CPU` не содержит tagword, FIP/FDP и last opcode. x87 вычисления используют double вместо полной 80-bit арифметики, как upstream. Эти ограничения особенно важны для проверки сетевого детерминизма.

Сборка после размещения wasi-sdk 34 в `var/toolchains/`:

```sh
.venv/bin/python tools/build_runtime.py --jobs 8
```

По умолчанию используются `var/lift-compact/{war3,game,storm,ijl15}` и профиль памяти `compact`. DLL переведены с `--image-base`: game.dll → `0x02000000`, Storm.dll → `0x03000000`, ijl15.dll → `0x03100000`; war3.exe остаётся по `0x00400000`. Лифтер применяет только проверенные HIGHLOW-релокации, исходные PE не изменяет, SHA-256 считает по оригиналу. `wc3_load_at` повторяет релокации при загрузке оригинальных файлов. Старые `var/lift-v2` доступны только при явном `--memory-layout legacy`. Их можно задать через `--module-dirs`. `--objects-only` собирает независимые shards без линковки runtime. `--variant compat` собирает те же модули без хвостовых вызовов WebAssembly в `wc3-compat.wasm` и `build-compat.json`, с кэшем в `objects-compat/`. Переход `DISPATCH_TAIL` там выполняет трамплин вызывающей функции; сборщик добавляет `TAIL_RESUME` после каждого прямого вызова в копии шарда (`runtime-contract.md`). Обе сборки занимают около трёх минут на 16 потоках. Хеши source/header/compiler/flags управляют object cache. Встроенные библиотеки и исходники должны оставаться неизменными в процессе сборки; смена runtime headers требует повторного запуска.

Текущая компактная раскладка: окно гостя 512 MiB по адресу WASM `0x04000000`, доступная гостю ёмкость `0x1fff0000`, куча `0x04000000…0x1fff0000` (чуть меньше 448 MiB), основной стек заканчивается на `0x01fff000`. При инициализации WASM вырастает до 576 MiB плюс одна страница; native-стеки и другие выделения runtime идут за окном. Максимум общей WASM-памяти — 1 GiB. Builder проверяет пересечения DLL с кучей, TEB/PEB и стеком и записывает параметры в `build.json`; оба варианта обязаны иметь одинаковую раскладку.

Артефакты: `var/runtime/wc3.wasm` и `build.json`. Ниже — история измерений до компактной раскладки. Вынесенная `noinline`-проверка страниц при каждом обращении к памяти занимала около половины времени игрового потока (сборка 122 841 863 байта); встраивание полного обхода страниц давало 604 MB. Затем `wc3_mem_ptr` стал встроенно сравнивать начальный адрес с ёмкостью. Это ускорило игру, но сравнение, ветвление и вызов fault в каждом из миллионов мест обращения раздули сборку до 183 835 810 байт (gzip 21,1 МБ), а память JavaScriptCore для неё — на сотни мегабайт. Теперь в WebAssembly память гостя начинается с постоянного адреса `WC3_GUEST_BASE` (0x04000000, там кончается стартовая память runtime) внутри окна `WC3_GUEST_WINDOW` (2 GiB), которое принадлежит только гостю (`runtime/cpu.h`). `wc3_init` растит память до конца окна и ещё 16 байт; собственные выделения runtime (native-стеки и TLS потоков, буферы) лежат ниже окна или после него, потому что аллокатор берёт память с текущего конца. `wc3_mem_ptr` накладывает на адрес маску окна, а постоянную базу компилятор кладёт в смещение инструкции загрузки: память runtime недостижима без сравнения и ветвления. Сборка — 123 727 255 байт (gzip 12,8 МБ). В Chromium время главного гостевого потока на кадр меньше на 6–11% (меню 2,32 → 2,17 мс, сохранённая игра 2,62 → 2,33 мс). Пик памяти системного JavaScriptCore при компиляции 1,59 → 0,99 ГБ. Процесс страницы WebKit: запуск 868 → 557 МБ, пик перехода в меню 1229 → 914 МБ, меню 1024 → 830 МБ. Адрес за ёмкостью теперь не вызывает fault: он попадает в неиспользуемый хвост окна, а от 2 GiB — в младшую половину памяти гостя. Валидная программа так не обращается: пользовательское пространство Win32 у программы без large address aware кончается ниже 2 GiB. Нативные тестовые сборки (не WebAssembly) сохраняют `g_mem` из `malloc` и проверку границ; тестовые WASM-сборки задают маленькое окно через `-DWC3_GUEST_BASE`/`-DWC3_GUEST_WINDOW`. Строгая проверка страниц (`--strict-memory`) остаётся для поиска ошибок эмуляции памяти: валидная программа не обращается к NOACCESS-страницам, а гостевой SEH такой fault всё равно не обрабатывает. Стек и TEB потока проверяются строго (`wc3_mem_check`) в любой сборке. WASI SDK 34 не принимает `-mexec-model=reactor` для threads target, поэтому скрипт явно линкует штатный `crt1-reactor.o` с `--no-entry` и экспортом `_initialize`.

`build.json` содержит SHA-256 WASM, ожидаемые хеши исходных игровых модулей (`modules[].sha256`), их `image`, `liftDirectory` и `symbol`, настройки памяти и отрицательные статусы `playable`, `campaign_verified`, `multiplayer_verified`. Хеш каждого PE должен быть проверен до передачи его в runtime: переведённый код относится к конкретным байтам установки.

Проверено тринадцатью CPU/lifter tests и двумя builder tests: атомарные операции, арифметические флаги, четыре параллельных потока с общим счётчиком, unaligned доступ, явная ошибка невыровненного LOCK, reserve→commit и доступ через границы страниц, сохранение CPU ABI, несколько code sections, data/code callbacks без relocations, отказ от неполной генерации и инвалидирование object cache при изменении source. Успешные тесты и линковка не заменяют проверку оригинального меню и игрового процесса.
